Playbooks in Cortex XSOAR are stored as YAML files that conform to the COPS (Common Open Playbook Standard). Each file fully describes a workflow — its tasks, the connections between them, the inputs each task receives, and the conditions that determine execution flow. Understanding the YAML structure lets you build playbooks programmatically, review them in pull requests, and contribute them back to the community.

<Warning>
  Every playbook YAML must have a corresponding `_README.md` documentation file in the same directory. The `demisto-sdk` validation step will fail if the README is missing or empty.
</Warning>

## Playbook YAML Structure

A playbook file has a small set of top-level keys followed by the `tasks` map, which contains every node in the graph.

```yaml
id: My Playbook Name
name: My Playbook Name
version: -1
description: >-
  A one-paragraph description of what this playbook does, when it is triggered,
  and what integrations or sub-playbooks it depends on.
starttaskid: "0"
inputs:
  - key: IPAddresses
    value: {}
    required: false
    description: A comma-separated list of IP addresses to enrich and block.
    playbookInputQuery:
outputs:
  - contextPath: BlockedIPs
    description: List of IP addresses that were successfully blocked.
    type: string
tasks:
  ...
```

### Top-Level Fields

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique identifier. By convention matches `name`. |
| `name` | string | Human-readable display name shown in the XSOAR UI. |
| `version` | integer | Always `-1` in source; the server manages the live version. |
| `description` | string | Describes purpose, trigger conditions, and integration dependencies. |
| `starttaskid` | string | The ID of the start task — always `"0"` by convention. |
| `inputs` | list | Declared playbook inputs that callers (or sub-playbook invocations) can pass in. |
| `outputs` | list | Context paths this playbook writes to and that parent playbooks can reference. |
| `tasks` | map | The full graph — keys are string task IDs, values are task objects. |

## Task Object Structure

Each entry in the `tasks` map is a task object with the following shape:

```yaml
tasks:
  "7":
    id: "7"
    taskid: 3bfa1467-a97a-41e0-b4d2-example00000   # UUID generated by XSOAR
    type: condition                                  # start | title | regular | condition | playbook
    task:
      id: 3bfa1467-a97a-41e0-b4d2-example00000
      version: -1
      name: Is the IP address malicious?
      description: Check DBotScore before blocking.
      type: condition
      iscommand: false
      brand: ""
    nexttasks:
      "yes":
        - "8"
      '#default#':
        - "2"
    conditions:
      - label: "yes"
        condition:
          - - operator: greaterThanOrEqual
              left:
                value:
                  complex:
                    root: DBotScore
                    filters:
                      - - operator: isEqualString
                          left:
                            value:
                              simple: DBotScore.Indicator
                            iscontext: true
                          right:
                            value:
                              simple: inputs.IPAddresses
                            iscontext: true
                    accessor: Score
                iscontext: true
              right:
                value:
                  simple: "3"
    separatecontext: false
    quietmode: 0
    continueonerrortype: ""
```

### Key Task Fields

| Field | Description |
|-------|-------------|
| `id` | String identifier used in `nexttasks` references within this file. |
| `taskid` | UUID that XSOAR uses as the canonical internal key. |
| `type` | Execution type: `start`, `title`, `regular`, `condition`, or `playbook`. |
| `task.name` | Label shown on the node in the visual editor. Use **verb-noun** format (e.g. *Enrich IP address*, *Block malicious domain*). |
| `task.iscommand` | `true` when `task.script` references a live integration command (`Brand\|\|\|command`); `false` for scripts and sub-playbooks. |
| `task.script` | For `regular` tasks: `Brand\|\|\|command-name` (integration command) or `ScriptName` (automation script). |
| `nexttasks` | Map of branch labels to arrays of downstream task IDs. `'#none#'` for unconditional; `'#default#'` for the condition fallback. |
| `conditions` | Array of labelled condition blocks evaluated in order; the first matching label determines the branch taken. |
| `separatecontext` | If `true`, the sub-playbook runs in its own context copy (used for looping). |
| `skipunavailable` | If `true`, skip this task if the required integration is not configured. |
| `quietmode` | Controls war-room verbosity: `0` = full output, `2` = quiet. |

## Minimal Playbook Example

The following snippet shows a complete minimal playbook: a start task fans out to a regular enrichment task and a condition; the condition either proceeds to a blocking task or terminates.

```yaml
id: Block Malicious IP - Example
name: Block Malicious IP - Example
version: -1
description: Enrich an IP address and block it if the DBotScore is 3 (malicious).
starttaskid: "0"
inputs:
  - key: IPAddress
    value: {}
    required: true
    description: The IP address to evaluate.
tasks:
  "0":
    id: "0"
    taskid: 00000000-0000-0000-0000-000000000000
    type: start
    task:
      id: 00000000-0000-0000-0000-000000000000
      version: -1
      name: ""
      iscommand: false
      brand: ""
      description: ""
    nexttasks:
      '#none#':
        - "1"
    separatecontext: false

  "1":
    id: "1"
    taskid: 11111111-1111-1111-1111-111111111111
    type: regular
    task:
      id: 11111111-1111-1111-1111-111111111111
      version: -1
      name: Enrich IP address
      description: Query threat intelligence for the given IP.
      script: ip
      type: regular
      iscommand: true
      brand: ""
    nexttasks:
      '#none#':
        - "2"
    scriptarguments:
      ip:
        simple: ${inputs.IPAddress}
    separatecontext: false

  "2":
    id: "2"
    taskid: 22222222-2222-2222-2222-222222222222
    type: condition
    task:
      id: 22222222-2222-2222-2222-222222222222
      version: -1
      name: Is IP malicious?
      description: Branch based on DBotScore.
      type: condition
      iscommand: false
      brand: ""
    nexttasks:
      "yes":
        - "3"
      '#default#':
        - "4"
    conditions:
      - label: "yes"
        condition:
          - - operator: isEqualNumber
              left:
                value:
                  simple: DBotScore.Score
                iscontext: true
              right:
                value:
                  simple: "3"
    separatecontext: false

  "3":
    id: "3"
    taskid: 33333333-3333-3333-3333-333333333333
    type: playbook
    task:
      id: 33333333-3333-3333-3333-333333333333
      version: -1
      name: Block IP - Generic v3
      playbookName: Block IP - Generic v3
      type: playbook
      iscommand: false
      brand: ""
      description: ""
    nexttasks:
      '#none#':
        - "4"
    scriptarguments:
      IP:
        simple: ${inputs.IPAddress}
    separatecontext: true

  "4":
    id: "4"
    taskid: 44444444-4444-4444-4444-444444444444
    type: title
    task:
      id: 44444444-4444-4444-4444-444444444444
      version: -1
      name: Done
      type: title
      iscommand: false
      brand: ""
      description: ""
    separatecontext: false
```

## Playbook Conventions

The `demisto/content` repository follows a set of authoring conventions that keep playbooks consistent and maintainable across 1,300+ Packs.

**Use generic playbooks for reusable logic.** Name them with the pattern `<Action> <Entity> - Generic`, for example `Block IP - Generic v3` or `Enrich Domain - Generic`. Generic playbooks try every enabled integration and degrade gracefully when one is absent (`skipunavailable: true`).

**Name tasks in verb-noun format.** Good task names read like imperative instructions: *Enrich IP address*, *Check if user is VIP*, *Send notification to analyst*. Avoid vague names like *Step 1* or *Do thing*.

**Decompose complex logic into sub-playbooks.** If a sequence of tasks makes sense as a standalone unit (e.g. all the steps to isolate an endpoint), extract it into its own playbook file and call it with `type: playbook`. This mirrors the Single Responsibility Principle and makes each piece testable independently.

**Version breaking changes.** When a playbook change would break existing callers (new required inputs, renamed outputs), create a new file with a `_v2` (or `_v3`, etc.) suffix rather than editing the original. The old version remains available for existing automations while new callers adopt the latest.

## File and Directory Layout

```
Packs/
└── MyPack/
    ├── Playbooks/
    │   ├── MyPlaybook.yml            # Playbook definition (COPS YAML)
    │   └── MyPlaybook_README.md      # Required documentation file
    └── TestPlaybooks/
        └── MyPlaybook-Test.yml       # Test playbook verifying the main one
```

- Place every production playbook under `Packs/<PackName>/Playbooks/`.
- The README must document inputs, outputs, dependencies, and a usage example.
- Test playbooks live in `Packs/<PackName>/TestPlaybooks/` and exercise the main playbook against mock integrations in CI.

## Creation Workflow

<Steps>
  <Step title="Design the workflow">
    Map out the incident response procedure on paper or in a whiteboard diagram. Identify the inputs, the integrations involved, the conditions that gate each decision, and the terminal states (close as true positive, close as false positive, escalate to analyst).
  </Step>
  <Step title="Build in the XSOAR visual editor">
    Use the drag-and-drop playbook editor in the XSOAR UI to add tasks, connect them, and configure arguments by referencing context paths. The editor validates connections in real time and generates the YAML automatically.
  </Step>
  <Step title="Export the YAML">
    Export the playbook from the XSOAR UI to obtain the COPS-format YAML file. Place it at `Packs/<PackName>/Playbooks/<PlaybookName>.yml` in your local clone of the content repository.
  </Step>
  <Step title="Write the README">
    Create `Packs/<PackName>/Playbooks/<PlaybookName>_README.md`. Document every input and output, list integration dependencies, and include a screenshot of the visual graph if possible.
  </Step>
  <Step title="Add a test playbook">
    Create a test playbook under `Packs/<PackName>/TestPlaybooks/` that exercises the main playbook with known-good inputs and asserts expected context values on completion.
  </Step>
  <Step title="Validate and format">
    Run `demisto-sdk format -i Packs/MyPack/Playbooks/MyPlaybook.yml` to normalise the YAML, then `demisto-sdk validate -i Packs/MyPack/Playbooks/` to check for schema and convention errors before opening a pull request.
  </Step>
</Steps>
